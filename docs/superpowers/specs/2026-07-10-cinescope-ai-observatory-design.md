# CineScope AI 电影观测站设计规格

- 日期：2026-07-10
- 状态：已批准
- 产品方向：70%「AI 电影观测站」+ 30%「空间化神经影院」
- 适用项目：`douban-taste-recommender`
- 视觉草图：`.superpowers/brainstorm/749-1783665151/content/`

## 1. 背景

当前项目已经具备豆瓣同步、候选抓取、电影/电视剧/动漫分类、推荐解释、海报多源补图、人物补图、详情抽屉、推荐快照和“换一批”等能力，也已有 229 个自动化测试作为回归基线。

主要问题不再是“有没有功能”，而是功能、数据与界面缺少统一架构：

- `web_ui.py` 约 146 KB，HTML、CSS、状态、网络请求与渲染逻辑耦合在一个字符串中。
- `douban_sources.py` 与 `curated_catalog.py` 均超过 80 KB，来源适配、身份解析与资料合并边界不清晰。
- 推荐结果数量、当前批次数量和可用候选数量容易被混为一谈。
- 图片依赖外部热链与临时补图，网络异常会直接暴露为用户可见问题。
- 演员与导演照片仅按姓名尝试搜索，缺少稳定的人物身份图谱。
- 当前页面仍像高级数据面板，不像真正的私人 AI 流媒体产品。
- 详情抽屉、长页面、瘦长卡片和空旷侧栏削弱了视觉冲击与浏览效率。
- 刷新、深链、批次和同步状态尚未形成统一的可恢复状态模型。

本次重构将保留已经验证的爬虫、资料解析和推荐基线，重建产品架构、前端结构、推荐会话、媒体可信管线和持久状态。

## 2. 产品目标

### 2.1 核心目标

1. 让用户从进入产品到决定“今晚看什么”的路径足够快，同时允许高级用户进入空间化探索。
2. 推荐电影、电视剧和动画剧集；动画频道必须排除动画电影，电视剧默认降低古装内容优先级。
3. 推荐以高质量与剧情表现为基础，不把用户简化成一组僵硬的喜欢/不喜欢标签。
4. 任何可见海报、背景图、演员或导演位置都不能出现浏览器破图、空白媒体框或无限加载。
5. 错图比缺少真实图片更严重；无法确认身份时必须展示明确标记的设计兜底图。
6. 刷新后恢复上次空间、频道、推荐批次、滚动位置、详情深链和候选托盘。
7. 保持本地、非商业化、一键运行；不要求用户购买 API 或安装 Node 运行时。
8. Cookie 只由用户输入并存于 `sessionStorage`，不读取浏览器 Profile、不落盘、不回显。

### 2.2 非目标

- 不构建社交网络、订阅收费、广告、会员或内容播放系统。
- 不抓取或保存代理订阅地址。
- 不使用大语言模型直接生成不存在的影片、人物或评分。
- 不为了框架标签将项目改造成需要复杂部署的云服务。
- 不承诺互联网上每一位演职人员都存在可公开验证的真人照片；承诺界面永远完整并清楚区分真人图与设计兜底。

## 3. 北极星体验

产品采用双模式：

- **观影模式（70% A）**：默认模式，电影级 Hero、紧凑货架、快速比较和可解释推荐，目标是高效做出选择。
- **宇宙模式（30% C）**：按需展开作品、题材、导演、演员和口味信号的空间关系，用于发现跨类型路径。

两者不是两个独立产品。任何推荐卡、详情页或人物页都可以进入宇宙模式；从宇宙模式返回时保留原推荐上下文。

### 3.1 五个顶级空间

| 空间 | 职责 | 默认行为 |
| --- | --- | --- |
| 今夜策展 | 快速推荐、频道浏览、换一批、比较和最终选择 | 登录产品后的默认空间 |
| 发现宇宙 | 作品、人物、题材与口味关系图 | 按需加载 Canvas 图谱 |
| 私人片库 | 看过、想看、候选、稍后看、已拒绝 | 支持筛选、撤销和导出 |
| 口味 DNA | 稳定偏好、矛盾偏好、近期漂移和探索盲区 | 所有信号都可查看来源 |
| 同步与数据健康 | 豆瓣同步、缓存、媒体任务、来源健康和隐私状态 | 不污染主推荐流程 |

电影、电视剧和动画剧集属于“今夜策展”的内容频道，而不是顶层空间。综合频道可以混合三类内容，但每一类都有独立候选池和批次游标。

### 3.2 全局 AI Command Lens

AI Command Lens 在任何空间可通过 `Ctrl+K` 唤起：

- 顶部时是紧凑输入镜。
- 页面滚动后收为不遮挡内容的发光 Orb。
- 打开后显示自然语言输入、解析后的可编辑条件和推荐结果影响预览。
- 可以进入多轮策展对话，但不会替代页面导航。

示例：

> 今晚想看聪明、悬疑、群像，但不要太压抑的动画剧集，最好一集 30 分钟以内。

解析结果必须显示为可编辑条件，例如：媒介=动画剧集、节奏=中快、复杂度=高、强度≤中、单集≤30 分钟、避开=过度压抑。

## 4. 信息架构与路由

前端使用真实可恢复路由，推荐使用 History API；服务器对未知前端路径返回 `index.html`。

| 路由 | 内容 |
| --- | --- |
| `/tonight` | 综合策展 |
| `/tonight/movie` | 电影频道 |
| `/tonight/series` | 电视剧频道 |
| `/tonight/anime-series` | 动画剧集频道 |
| `/universe` | 发现宇宙 |
| `/library` | 私人片库 |
| `/taste` | 口味 DNA |
| `/health` | 同步与数据健康 |
| `/title/<canonical-id>` | 沉浸式作品详情 |
| `/person/<canonical-id>` | 人物详情 |

刷新必须恢复：

- 当前空间和频道；
- 当前推荐会话与批次；
- 频道内滚动位置；
- 已展开详情或人物路由；
- 候选托盘；
- 尚未提交的 Command Lens 条件。

同步不再是强制三步首页。首次使用显示轻量欢迎层；完成一次同步后，后续启动直接恢复上次推荐现场。同步失败时保留现有数据，不出现空白页。

## 5. 推荐与 AI 设计

### 5.1 双引擎边界

推荐系统由两个职责严格分离的引擎组成：

1. **本地口味与排序引擎**
   - 执行候选过滤、质量计算、口味匹配、情境匹配、多样性重排、置信校准和批次管理。
   - 所有结果可复现、可测试，不依赖语言模型。
2. **语言交互引擎**
   - 将自然语言解析成结构化意图，组织比较和解释文本。
   - 默认使用本地规则与词典解析器即可完整工作。
   - 可选自动探测本地 Ollama 或用户配置的 OpenAI-compatible 端点。
   - 语言模型只能引用本地证据对象，不得自行生成标题、人物、评分或事实。

### 5.2 结构化意图

`RecommendationIntent` 至少包含：

- `media_types`
- `genres`
- `moods`
- `pace`
- `complexity`
- `intensity`
- `runtime_minutes`
- `episode_runtime_minutes`
- `countries`
- `languages`
- `year_range`
- `quality_floor`
- `avoid`
- `exploration_level`
- `surprise_level`
- `session_only_adjustments`

用户说“今晚不想看慢热”只写入当前推荐会话；用户明确选择“以后少推荐慢热”才进入长期偏好。

### 5.3 七层推荐管线

#### 第一层：资格过滤

硬过滤在打分前执行：

- 排除已经看过的条目；
- 排除明确永久拒绝的条目；
- 严格匹配请求媒介；
- 动画剧集频道排除电影、OVA 电影合集和无法确认剧集格式的条目；
- 电视剧默认排除或显著降低古装内容，除非用户本次明确要求；
- 排除标题占位、身份冲突、资料置信度过低的候选。

#### 第二层：质量先验

质量分综合：

- 豆瓣评分及投票数的贝叶斯校正；
- 其他可信来源评分只作辅助信号；
- 剧情简介、类型、年份、地区、主创资料完整度；
- 候选来源质量；
- 用户强调的“高评分 + 剧情好”。

评分高但投票数过少时不直接压过大量稳定高分作品。

#### 第三层：口味匹配

口味模型区分：

- 长期稳定正向偏好；
- 长期负向偏好；
- 允许共存的矛盾偏好；
- 最近 30/90 天的偏好漂移；
- 高分条目与低分条目的特征差；
- 用户主动反馈。

模型不得把“题材覆盖广”误判为没有偏好；应学习用户更稳定的剧情结构、节奏、人物关系和质量阈值。

#### 第四层：当下情境

根据 Command Lens 意图调整时长、节奏、复杂度、强度、情绪和避雷项。本层只影响当前会话，除非用户明确将条件保存为长期偏好。

#### 第五层：多样性重排

使用质量保护的 MMR 类重排，避免连续出现：

- 相同国家；
- 相同年代；
- 相同题材组合；
- 相同导演或演员；
- 同一动画地区与风格；
- 过多日漫。

多样性不能把低质量条目抬到高质量条目前；只有在基础分差距合理时进行替换。

#### 第六层：置信校准

每条结果输出：

- 质量分；
- 长期口味分；
- 当前情境分；
- 探索价值；
- 总匹配分；
- 置信度；
- 强理由；
- 冲突信号。

资料不足时显示“判断依据有限”，不输出伪精确分数。

#### 第七层：批次策展

每个频道拥有独立候选池、独立游标和独立历史：

- 候选池目标数量与当前展示数量始终分别显示。
- 例如：`160 个候选 → 47 个条件命中 → 当前第 3 批 9 部`。
- 当前批次建议桌面显示 9–12 部，移动端 6–8 部。
- 在候选池耗尽前不重复展示已浏览条目。
- “换一批”立即从本地池生成，不依赖再次联网。
- 支持撤回上一批。
- 支持选择换批原因：太相似、太沉重、看过太多、节奏不对、给我惊喜。

### 5.4 反馈事件

反馈不再只有喜欢/不喜欢：

| 事件 | 作用域 |
| --- | --- |
| 想看 | 长期片库 |
| 已看过 | 长期片库并从候选排除 |
| 加入今晚候选 | 当前会话 |
| 不适合今晚 | 当前会话 |
| 少推荐这种节奏/题材 | 长期弱负反馈 |
| 永久避开 | 长期强负反馈 |
| 资料或图片错误 | 数据纠错 |
| 撤销 | 恢复前一状态 |

所有反馈事件保留来源和时间，可在私人片库或口味 DNA 中撤销。

### 5.5 可解释性

卡片只展示一个短理由和一个冲突提示。详情页展示完整四维分解和证据：

- 关联到用户哪些高分作品；
- 哪些质量信号最强；
- 当前请求如何改变排序；
- 为什么它被用于增加多样性；
- 哪些信号与用户偏好冲突。

## 6. 媒体可信架构

### 6.1 核心原则

1. 浏览器不直接加载第三方图片 URL。
2. 任何 `<img>` 只有在本地资产状态为 `ready` 后才插入 DOM。
3. 外部图片先经身份匹配、下载、字节验证、解码和本地缓存。
4. 无法确认时使用稳定设计兜底，不使用可能错误的图片。
5. 海报、背景、导演和演员图片使用同一资产状态机。

### 6.2 数据模型

SQLite 增加以下核心实体：

- `media_identity`：作品规范身份、标题、原名、年份、媒介、地区。
- `provider_identity`：Douban、TMDb、IMDb、TVMaze、AniList、MAL、Wikidata 等外部 ID。
- `person_identity`：人物规范身份、名称、别名和来源 ID。
- `credit`：作品与人物的导演、演员、声优、编剧等关系。
- `asset_candidate`：外部图片候选、来源、类型、身份证据、尺寸和置信度。
- `asset_file`：本地文件哈希、MIME、宽高、大小、状态和最后验证时间。
- `resolution_job`：任务优先级、当前来源、进度、失败原因、退避和重试时间。
- `user_asset_override`：用户确认的正确或错误映射。

### 6.3 身份匹配

作品图片自动接受必须满足：

- 规范标题或原名精确匹配；
- 媒介类型一致；
- 年份一致或误差不超过一年；
- 若标题存在歧义，国家、导演、演员、集数或制作公司至少再命中一项。

仅标题相同不得自动接受。模糊匹配只能生成候选，不能直接替换现有图。

人物图片自动接受必须满足：

- 人物姓名或已知别名匹配；
- 来源实体确认是人物；
- 与当前作品存在可验证演职员关系，或外部人物 ID 已绑定；
- 同名歧义时必须有职业、国籍、作品或出生信息的辅助证据。

### 6.4 来源顺序

来源按媒介动态选择：

- 电影：TMDb API（有 Key 时）→ OMDb/IMDb（有 Key 时）→ TMDb 公共页 → Wikidata/Wikipedia → Douban。
- 电视剧：TVMaze → TMDb → Wikidata/Wikipedia → Douban。
- 动画剧集：AniList → Jikan/MAL → TMDb/TVMaze → Douban。
- 人物：已绑定作品来源的 cast/crew API → Wikidata/Wikipedia → Jikan/MAL 人物 → Douban 公开人物页。

单个来源具备并发上限、指数退避和熔断状态。来源健康在“同步与数据健康”空间可见。

### 6.5 下载与验证

下载后必须执行：

- HTTP 状态检查；
- `Content-Type` 检查；
- JPEG/PNG/WebP 等魔数检查；
- 完整像素解码；
- 最小尺寸和长宽比检查；
- HTML、验证码和反爬页面拒绝；
- SHA-256 去重；
- 可选生成响应式缩略图。

资产保存到用户数据目录的 `media/`，文件名使用内容哈希。浏览器通过 `/media/<hash>` 获取，并使用不可变缓存头。

### 6.6 资产状态机

`unknown → queued → resolving → downloading → validating → ready`

异常分支：

- `degraded`：真实图片暂不可用，但设计兜底正常。
- `ambiguous`：存在多个身份候选，需要更多证据或人工确认。
- `backoff`：来源限流或短期失败。
- `rejected`：图片或身份验证失败。

状态变化通过任务事件推送或短轮询更新界面。详情中的“补全资料”必须显示具体来源、当前步骤和结果，不允许点击后无反馈。

### 6.7 零破图交付

- 首屏海报和人物优先级最高。
- 当前批次完成后预取下一批。
- 详情打开前优先补全导演和前 8 位演员。
- 真实图未就绪时使用与最终尺寸一致的设计卡，避免布局跳动。
- 运行时图片解码失败立即切换设计卡，并将本地资产标记为失效以触发修复。
- 设计卡明确标记“资料图待核验”或“暂无精确海报”，不伪装成真人图。

### 6.8 代理与隐私

- 自动探测常见本地 HTTP 代理端口，如 7890、7897、10809。
- 用户可配置本地 `http://127.0.0.1:<port>`。
- 不接收、不读取、不保存代理订阅地址。
- 网络请求优先使用配置代理，连接拒绝后允许直接连接回退。
- Cookie 不参与第三方媒体请求。

## 7. 同步与候选数据

### 7.1 豆瓣用户识别

接受：

- 完整豆瓣个人主页 URL；
- 纯用户 ID；
- 带查询参数的主页 URL。

解析后只保存规范主页 URL 与用户 ID。主页输入可以长期记忆；Cookie 只能会话记忆。

### 7.2 分页策略

- 用户界面默认显示“自动抓取到末页”，不要求用户决定页数。
- 后端以空白分页、连续重复页或明确登录拦截作为停止条件。
- 使用高位安全阀防止异常循环，默认 250 页；该值不作为正常推荐数量限制。
- 看过与想看分别报告抓取页数、成功条数、重复条数、失败页和停止原因。
- 部分分页失败时保留成功数据并允许从失败页继续。

### 7.3 Cookie 流程

- 首次需要登录态时给出复制教程与粘贴位置。
- 用户勾选“本次会话记住”后写入 `sessionStorage`。
- 请求发送后后端只在当前处理和必要的短生命周期任务内存中使用。
- 后端日志、响应、SQLite、导出文件和错误信息不得包含 Cookie。
- 不读取浏览器 Profile 或浏览器 Cookie 数据库。

## 8. 详情、人物与宇宙交互

### 8.1 作品详情

详情改成全屏沉浸路由，而不是狭窄抽屉：

- 横向背景图负责氛围，竖向海报使用 `object-fit: contain`，不互相替代。
- 顶部展示标题、年份、类型、评分、无剧透简介、匹配分和主要动作。
- 主要区块：为什么推荐、剧情与资料、演职人员、关系宇宙、相似作品。
- 标签栏在滚动后保持可见。
- 从卡片进入时使用共享元素转场；刷新详情路由仍可独立恢复。

### 8.2 人物体验

- 演职员采用横向人物画廊，不在狭窄区域纵向堆积。
- 点击人物先打开同源侧层，显示身份、角色、与用户片库的关系和代表作品。
- 再进入完整人物路由查看全部相关候选。
- 真实照片和设计身份卡均显示来源状态。
- 人物页可执行“更多该导演/演员作品”“加入探索条件”等动作。

### 8.3 宇宙模式

- 使用 Canvas 2D 按需渲染，不增加默认首页负担。
- 初始只展示 5–9 个高价值节点。
- 支持拖动、缩放、聚焦和逐层展开。
- 关系边必须有文本解释，如“同导演”“共享高分偏好：群像”“节奏相似”。
- 任何节点可回到常规详情和推荐会话。

## 9. 视觉与动效系统

### 9.1 视觉语言

- 深黑曜石背景；
- 低饱和青、紫作为空间和 AI 信号；
- 金色只用于关键动作和策展强调；
- 大标题使用紧凑字距，正文保持高可读性；
- 玻璃材质只用于浮层和 AI Lens，不铺满所有卡片；
- 使用细微颗粒和光晕，不依赖重图片滤镜制造高级感。

### 9.2 密度与页面长度

- 桌面推荐卡默认 5–6 列，保持稳定 2:3 海报比例。
- 标题最多两行，推荐理由最多三行。
- 快速动作在悬停、聚焦或移动端展开时出现。
- 频道采用横向货架、分段加载和必要时虚拟化，避免超过 4000px 的卡片长墙。
- 左侧导航默认 72px，可完全隐藏；内容是主干。

### 9.3 动效预算

- 微交互：160–220ms。
- 卡片与面板：220–320ms。
- 沉浸式模式切换：320–480ms。
- 只优先动画 `transform` 与 `opacity`。
- 悬停快速预览延迟约 180ms，并设置安全离开区域避免误触。
- 完整支持 `prefers-reduced-motion`。

### 9.4 可访问性

- 全功能键盘导航；
- 清晰焦点环；
- 对话框和侧层焦点锁定；
- 图片状态提供文本；
- 颜色不是唯一状态信号；
- 对比度满足 WCAG AA；
- 触控目标不小于 40px。

## 10. 技术架构

### 10.1 总体选择

采用：

- Python 标准库本地 HTTP 服务继续作为运行入口；
- 原生 HTML/CSS/ES Modules 前端，无 Node 运行依赖；
- SQLite 管理持久数据、推荐会话和媒体清单；
- 本地哈希媒体仓库；
- 线程池执行同步、媒体解析与预取任务；
- 现有 `web.py` 暂时作为兼容入口，内部逐步委托给新模块。

不采用 React/FastAPI 的原因不是能力不足，而是当前产品的首要风险是可靠性、迁移复杂度和本地一键运行。原生模块足以完成目标交互，同时减少构建链和运行依赖。

## 11. 迁移策略

1. 为当前 229 个测试建立基线报告。
2. 新增 SQLite 和 repository，不立即替换现有 CSV/快照读取。
3. 为旧数据增加一次性迁移：过滤编号占位标题、错误 premium 海报和人物占位身份。
4. 把媒体解析与缓存从 `web.py`、`douban_sources.py` 抽成独立服务。
5. 新前端先使用现有 API，建立应用壳、路由和状态恢复。
6. 引入 `/api/v2` 推荐会话与批次，再切换推荐页面。
7. 迁移详情、人物、宇宙和健康中心。
8. 保留 legacy UI 启动开关，直到新 UI 完成全部验收。
9. 验收后让默认入口指向新 UI，并删除仅服务旧 UI 的重复逻辑。

迁移过程不得覆盖用户现有未提交代码和本地数据。

## 12. 错误处理

- 任一后台任务失败都返回结构化 `error_code`、可读说明、已完成数据和可重试位置。
- 同步部分失败时使用已有缓存继续推荐。
- 媒体失败只影响真实图覆盖，不影响布局、详情和推荐。
- 推荐算法遇到资料不足时降低置信度，不让请求整体失败。
- 路由渲染异常显示局部恢复面板，不显示空白页。
- 每个空间有独立错误边界和“恢复上次稳定状态”动作。
- 任务日志自动清理 Cookie、API Key 和代理凭据。

## 15. 已锁定决策

- 70% A + 30% C 双模式。
- 五个顶级空间。
- 全局 AI Command Lens。
- 本地排序是事实来源，LLM 仅做可选语言增强。
- 七层推荐管线和独立频道批次。
- 浏览器只消费本地可信媒体。
- 错图宁可不用；兜底图必须清楚标记。
- 原生 ES Modules 前端、Python 本地服务、SQLite 和本地媒体仓库。
- Cookie 仅 `sessionStorage`；不读取浏览器 Profile。
- 不保存代理订阅地址，只探测或配置本地代理端口。
- 用户已授权后续设计、实施和验收由 Codex 自主迭代，不再逐章请求确认。
